# Owned native item gameplay adapter

`src/main_item_gameplay.rs` is a bin adapter for `RuntimeGameplayHooks`, rather than a replacement for all `ServerPlayer` behavior. Its explicit `NativeFixtureEmptyCriteria` policy owns new empty advancement registrations and statistic objectives. `UnknownImported`, source invalidation and any unported nonempty registry produce errors. `PlayerPhaseScope::NativeItemCallbacksOnly` explicitly excludes full level `ServerPlayer.tick` and connection `ServerPlayer.doTick`.

The pinned original is Minecraft 1.21, inner JAR SHA256 `8d47de9a76ab47186deba6c9beda6f9345c6f73618fa5a157c57608be0505a01`. The `main_item_gameplay_*_bytecode.txt` files contain original javap output; the executable helper calls the original classes and methods.

## Statistic and pickup order

Original `ServerPlayer.awardStat` (`aqv.a(Stat,int)`) first increments `ServerStatsCounter`, then calls `Scoreboard.forAllObjectives(stat, player, add(amount))`. The scoreboard indexes objectives by criterion identity. Its default empty list performs no score access, player-name access or score creation. The owned native fixture scoreboard has no objectives or scores. A recorded objective makes the guard fail before later supported item operations; it is not executed as a fake empty list. The real statistic values and dirty semantics come from `PlayerStats`, with the separate arithmetic/wire proof.

The working tree's post-v5 login hook also follows original `PlayerList.placeNewPlayer`: offsets490..494 call `player.getStats().markAllDirty()` on every successful login, before recipe-book initialization. Reconnecting after a previous send therefore re-publishes every existing key, including stored zero and saturated values. A fresh UUID still has no stored keys. Native values currently survive same-process UUID reconnects; native stat-file/restart persistence remains unimplemented. The archived v5 copy retains its earlier fresh-login scope. Current checker outputs use the separate `main-item-gameplay-login[-release]-conformance.json` names.

Original `ServerPlayer.onItemPickup(ItemEntity)` calls its superclass first. `LivingEntity.onItemPickup` resolves the owner and, when it is a ServerPlayer, invokes THROWN_ITEM_PICKED_UP_BY_ENTITY (`an.R`) on that owner with the picker as the context entity. Then the ServerPlayer override resolves the owner again and, when it is non-null, invokes THROWN_ITEM_PICKED_UP_BY_PLAYER (`an.S`) on the picker with the owner as the context entity. Thus the ordinary two-player path is stat → empty scoreboard → owner's R trigger → picker's S trigger.

`PickedUpItemTrigger.trigger` builds a real LootContext before the SimpleCriterionTrigger listener-map check. The oracle executes this construction too: it supplies the actual server/lookup and references the actual existing level RNG, with zero random draws. Only the environment getters are supplied; no trigger, scoreboard, counter or loot-context arithmetic is rewritten. Absent and explicitly empty current-player sets execute the original return path. A listener registered for an unrelated PlayerAdvancements identity also demonstrates the original identity-key gate, but the native empty-fixture policy conservatively rejects nonempty registrations.

The adapter's owner resolution is deliberately bounded to traced native Player.drop owners. It knows current and historical native player UUIDs. A current player owner triggers R then S; a departed known player resolves absent. An uncertified UUID requires actual Entity.getOwner resolution and errors. Arbitrary cached nonplayer references, imported entities and UUID aliasing are not claimed as implemented.

## InventoryChanged is independent

Original `aqv$2` is the ContainerListener. Its slotChanged method obtains the real menu Slot, skips ResultSlot, then checks backing-container identity against the player's Inventory. In InventoryMenu this admits slots 5..45 and excludes result/crafting 0..4 and the carried stack. `cg.trigger` scans all 41 Inventory slots before calling the empty listener gate, counting empty, occupied and full stacks. The adapter maps native InventoryMenu storage back to actual Inventory order and performs this scan at `inventory_slot_changed`.

The callback must be scheduled from a separate local AbstractContainerMenu lastSlots baseline. Its remoteSlots/predicted packet baseline cannot substitute: a predicted click can suppress a remote packet while a local criterion callback still runs. Main/menu integration owns that scheduling. The adapter does not infer it from network operations or returned packets.

The required `RuntimeGameplayHooks.inventory_slot_changed` hook validates the actual picker identity before entering this separate registry. RuntimeInventoryHost's successful pickup broadcast drains local changes and invokes this hook before menu publication, hence before later discard/count restoration/stat/onItemPickup. Normal menu broadcasting after an Inventory.add partial transfer returning false remains a separate level-player tick responsibility; the bounded phase counter alone does not implement that next-tick flush.

For atomic menu/drop actions, `prepare_menu_commit` checks the source scope and callback backing-container mapping, computes immutable empty-listener observations, and owns staged statistics without modifying the live owner. The exclusive prepared token can be dropped without effects. Its infallible commit assigns statistics and then the staged observations after world addition and before menu publication. Sharing the inventory scan among these immutable callbacks is valid only because the owned criterion sets are empty and cannot mutate inventory or emit advancement effects. A fourth native test checks rollback, commit and invalid callback identity, using original-derived full/empty counts and actual local container events.

This fixture policy is not the default vanilla advancement catalogue. The actual JAR contains 1,399 advancement files and 1,419 InventoryChanged criteria. Fourteen literal inventory predicates name minecraft:stone, including the stonecutter recipe. Vanilla also contains one R criterion for distracting a piglin and one S criterion for an allay delivery. Default recipe unlocks are explicitly unimplemented by this empty-fixture policy.

## Game-event source ownership

The owner materializes empty Euclidean registries on requested loaded chunk sections, including section Y outside build height. Main must certify the complete swept item region plus the event radius through its actual source backend after quiescence. Each game-event chunk query additionally requires manager health, no queued scheduler work and a successful current FULL future. An unconfirmed, pending or poisoned context returns an error; it never becomes a fabricated absent chunk. This is only the certified positive slice: original getChunkNow also has a four-entry FULL cache and visible-holder generation-FULL/allowed-status rules, which cannot generally be replaced by accessibility FULL. General cached/unloaded getChunkNow behavior is not implemented by this adapter. The dispatcher is the independently proved `post_to_empty_registries` implementation. No imported BE/entity list is treated as an empty registry certificate.

The existing original factory catalogue supplies all 490 listener-producing block states (sculk sensor, calibrated sensor, catalyst and shrieker families), and proves Item/ServerPlayer dynamic listener registration is inherited return-only behavior. Every primary and neighbour block mutation must call `observe_block_change`; listener-producing states block the supported floor. Unknown or imported entity/listener sources must invalidate coverage. Use the actual fresh, unedited startup fact, not merely the absence of an Anvil option. Saved native diffs need their own initial source scan/certificate.

Nonempty objectives, criteria or listener blocks are owned facts that require a later actual executor. The native adapter never treats those registries as empty. Diagnostic observations are bounded to 1,024 entries and have no network/gameplay significance.

## Reproduction and limits

`python3 tools/main_item_gameplay_generate.py` regenerates original fixtures; `python3 tools/main_item_gameplay_check.py` freshly replays originals, runs five native bin tests and writes `evidence/main-item-gameplay-login-conformance.json`. Add `--release` for the separate release report. The frozen v5 validation tree has the preceding four-test checker unchanged.

The original corpus has 920 scenes: 756 statistic/pickup combinations and 164 inventory scans. Native equality covers 336 supported pickup scenes and 164 inventory scenes, with 6,724 actual InventoryMenu slot callback applications. The other 420 pickup inputs are explicit nonempty-registry or uncertified-owner rejections, not counted as compatible scenes. Every actual original scene leaves level RNG unchanged. The inventory corpus includes every 1,333 prototype item ID; signed arithmetic extremes are covered by the pickup/counter paths.

This proof does not establish complete live player phases, default advancement/recipe behavior, full main menu-phase scheduling, imported listener dispatch, arbitrary owner-reference identity, stat-file persistence or global server compatibility. Main integration must preserve the module's declared source and phase scopes. The local container baseline and RuntimeInventoryHost callback have separate conformance reports; their full application wiring is not inferred from this adapter's unit corpus.
