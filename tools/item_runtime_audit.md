# Minecraft 1.21 dropped-item runtime audit

This is a bytecode audit of the unchanged official Java 1.21 server. It is **not** an executable conformance result or evidence that native item entities are integrated. No Rust source was changed by this audit.

The inner JAR SHA-256 is `8d47de9a76ab47186deba6c9beda6f9345c6f73618fa5a157c57608be0505a01`. The outer server SHA-1 is `450698d1863ab5180c25d7c804ef0fe6369dd1ba`. The companion JSON pins the generated bytecode evidence by SHA-256.

## Simulation and publication order

`ServerLevel.tick` calls `chunkSource.tick` at bytecode offset 298, before block events and the entity tick list at offset 447. `ServerChunkCache.tick(BooleanSupplier, boolean)` calls `ChunkMap.tick` (`aqb.l`) at offset 71. `ChunkMap.tick` calls each eligible `ServerEntity.sendChanges` at offset 194, gated by section change or the distance manager's ticking-range predicate.

Consequently, ordinary movement and dirty-data publication observe the item state **before** that level tick's `ItemEntity.tick`. Moving all items first and publishing their new state afterwards changes tick-level packet behavior. Player pickup happens later in the **connection phase**, through `ServerGamePacketListenerImpl.tick` → `ServerPlayer.doTick` → full `Player.tick/aiStep`, after all levels have finished. The level's `ServerPlayer.tick` does not invoke full `Player.tick`. See the independently checked [runtime entity order audit](runtime_entity_order_audit.md) for connection iteration, mounted pickup bounds and tracking lifecycle.

`EntityTickList` uses `Int2ObjectLinkedOpenHashMap`, preserving insertion order. If the active map is modified while it is being iterated, it copies into the spare map before the mutation. The current traversal continues over the old map. New entities added during the traversal are not ticked by that traversal. This must not be replaced by sorting entity IDs or by ticking all items then all players.

`ServerLevel.tickNonPassenger` calls `setOldPosAndRot`, increments entity `tickCount` with Java i32 overflow, then invokes the entity's tick. An integration must not increment a second time in `ItemState::tick`.

Spatial queries for merging and pickup have their own section/query order. The existing `Items::tick_all` BTree order is an explicitly limited convenience implementation; use a verified section-ordered query and the real mixed entity tick list for exact runtime behavior.

## Full item tick

`ItemEntity.tick` (`cjh.l`) performs these steps in order:

1. If the item stack is empty, discard and return before `Entity.tick`.
2. Invoke `Entity.tick`, which invokes the full `Entity.baseTick`.
3. Decrement a positive pickup delay except the infinite sentinel 32767.
4. Store the current position as this item tick's old position and capture the current velocity. This is **after** baseTick fluid effects.
5. If in water with fluid depth > `0.1f32`, apply water buoyancy; otherwise, if in lava with depth > that value, apply lava buoyancy; otherwise apply gravity.
6. On the server, set `noPhysics = !level.noCollision(item, bounds.deflate(1e-7))`. If embedded, run `moveTowardsClosestSpace(x, (minY+maxY)/2, z)`. On the client, `noPhysics` is false. This occurs before the movement gate.
7. Move if airborne, horizontal velocity squared > `1e-5f32`, or `(tickCount + entityId) % 4 == 0`. This invokes **full Entity.move**, then item friction/drag/bounce.
8. Determine whether the block position changed. Attempt neighbour merging every two ticks when changed, otherwise every 40 ticks, only on the server and when mergeable.
9. Increment age except the infinite-life sentinel -32768.
10. Run `updateInWaterStateAndDoFluidPushing` **again** and OR its result into `hasImpulse`.
11. On the server, set `hasImpulse` when current velocity minus the captured post-baseTick velocity has squared length > 0.01. This ORs with the existing flag; it does not reset it.
12. On the server, discard if age >= 6000.

The existing native scalar item tests deliberately override original `Entity.baseTick`, fluid updating, and `Entity.move` in the Java oracle. They prove the scalar item body under injected conditions, not the omitted generic entity/environment pipeline. The source explicitly supplies those operations through callbacks; the current callback shape cannot fully represent all missing state and effects.

### Missing generic base state and effects

`Entity.baseTick` includes vehicle-removal handling, boarding cooldown, old angles/walk fields, portal processing, sprint particles, powder-snow flags, fluid-height/flow updates, fluid at the eyes, swimming, fire damage/timer handling, lava damage, below-world removal, synced fire flags, and first-tick state. These operations can mutate velocity, health, metadata, removal state, RNG consumption and dimensions/portal state.

For example, the below-world check is `Y < level.minBuildHeight - 64`. `baseTick` clearing `firstTick` affects later fluid-entry effects. It is not safe to make these effects empty for all worlds.

### Missing embedded-space behavior

`Entity.moveTowardsClosestSpace` (`bsr.m(DDD)`) examines the five neighbours in order NORTH, SOUTH, WEST, EAST, UP; DOWN is excluded. It selects the nearest non-full-collision neighbour with strict distance improvement, retaining order on ties. The default direction is UP. It consumes one entity RNG float even when every neighbour is blocked. Speed is `nextFloat()*0.2f32 + 0.1f32`; the selected velocity axis is overwritten while the other axes are multiplied by 0.75.

This requires `noPhysics`, exact block-full-collision queries and entity RNG state. Returning a clipped geometric movement alone cannot reproduce it.

### Missing full movement behavior

`Entity.move` short-circuits for noPhysics. Otherwise it handles stuck-speed multipliers, piston restrictions, edge handling, full collision resolution, the position-update cutoff at squared movement <= 1e-7, support tracking, fall checks, horizontal velocity cancellation, block landing responses, `stepOn`, inside-block callbacks, block speed factor and fire/extinguishing effects.

Horizontal collision detection uses `Mth.equal` rather than exact equality; vertical collision detection uses exact comparison. Normal blocks reset vertical velocity on landing, while blocks such as slime and beds have distinct landing responses. Support selection affects subsequent friction lookup. `ItemEntity.getBlockPosBelowThatAffectsMyMovement` supplies `0.999999f32` to `Entity.getOnPos`; that helper can retain a supporting block's X/Z instead of just flooring the item centre. At block boundaries, `floor(x), floor(y-offset), floor(z)` is insufficient.

### Fluid algorithm prerequisites

`Entity.updateInWaterStateAndDoFluidPushing` clears the fluid-height map, updates water with push coefficient 0.014, then lava with coefficient 0.007 in ultrawarm dimensions or 0.0023333333333333335 otherwise. It returns whether the entity is in water or lava.

The fluid scan uses the bounding box deflated by 0.001 and X/Y/Z nested loops, with Z advancing fastest. Its fluid-surface position uses **f32 addition of block Y and fluid height before promotion to f64**. It tracks maximum immersion depth, scales shallow flows by that running depth, accumulates flows, averages by contributor count, normalizes the result for non-player entities, applies the push coefficient and a minimum impulse rule. Merely returning a cell's fluid height omits these velocity changes and the second update within the item body.

## Drop packet handlers

### Q, Ctrl+Q, F and release use

`handlePlayerAction` (`aru.a(ahm)`) updates last-action time before dispatch. Q, Ctrl+Q and F are ignored for spectators. Q calls `ServerPlayer.drop(false)`; Ctrl+Q calls `drop(true)`; F swaps hands then stops using the item. Release-use calls `releaseUsingItem`.

These branches return directly and **do not acknowledge the block-change sequence**. Only START/STOP/ABORT destroy dispatches acknowledge the sequence.

`Inventory.removeFromSelected(boolean)` returns empty if the selected stack is empty; otherwise it removes one or the full count. `ServerPlayer.drop(boolean)` updates the menu's remote selected-slot prediction before calling the three-argument player drop with `around=false, traceItem=true`.

### Creative negative slot

`handleSetCreativeModeSlot` first requires creative mode and an item enabled by world feature flags. Before assigning/dropping it, the handler may copy block-entity custom data when the stack's block-entity data contains x/y/z pointing at a loaded block entity.

Assignment slots are 1..45. An empty stack or one whose count <= effective max stack size is valid. Any negative slot denotes a drop, not only -1. A drop is accepted only while `dropSpamTickCount < 200`; accepted drops add 20 to that counter and listener ticks decrease a positive counter by one. The drop call is `player.drop(stack, true)`, whose wrapper means `around=false, traceItem=true`, with the normal pickup delay 40. It does not call `makeFakeItem` here.

### Player and server-player drop

`Player.drop` only creates the item and computes its exact RNG-dependent position/velocity. `ServerPlayer.drop` calls that method, then calls `level.addFreshEntity`, then awards the drop-item and total-drop stats when traceItem is true. The addFreshEntity result is ignored; the method still returns the constructed item. An empty stack returns before RNG consumption and world insertion.

The existing native drop kinematics and RNG proof covers this creation step, not world registration, menu remote-state updates, stats or advancement effects.

## Pickup

`Player.aiStep` touches nearby entities only when health > 0 and not a spectator. For an unmounted player it queries `bounds.inflate(1.0, 0.5, 1.0)`. Riding uses the min/max union of player and vehicle bounds, inflated `(1.0, 0.0, 1.0)`. It iterates non-XP entities in query order; XP orbs are collected separately and only one random candidate is touched.

`ItemEntity.playerTouch` is server-only and requires pickupDelay == 0, no mismatching target UUID, and successful `Inventory.add`. It then calls player `take(item, originalCount)`, discards if empty and restores the original stack count on the discarded object, awards item-picked-up statistics using **originalCount**, then invokes `onItemPickup`.

`ServerPlayer.take` invokes the inherited collect-packet behavior then immediately calls `containerMenu.broadcastChanges`. `ServerPlayer.onItemPickup` may trigger the thrown-item-picked-up-by-entity advancement using the resolved thrower. Neither the collect packet nor the picked-up stat uses just the accepted partial count. The native `accepted_count` remains useful for bookkeeping, but is not the Java packet/stat count.

## Tracker and pairing

Normal unmounted item tracking uses interval 20, trackDelta=true and no changing head rotation. Within an eligible `ServerEntity.sendChanges` call, packet order is velocity (if threshold), body movement, dirty metadata, then head rotation when relevant. Metadata dirtiness and hasImpulse force the interval gate. The end of that gate clears hasImpulse. `hurtMarked` is independent: after tickCount increments, it causes an additional velocity packet and is cleared, even if the normal gate was closed.

Pairing sends AddEntity, cached nondefault metadata, then an explicit velocity packet for non-living trackDelta entities, even though AddEntity already includes velocity. Both velocity fields use the tracker's lastSentMovement. AddEntity position and angles use the shared tracker base. Metadata uses the tracker's cached nondefault values, updated by `sendDirtyEntityData`; raw physical state may already contain dirty unpublished changes.

Future snapshots must distinguish physical state for simulation/visibility from the published tracker state for packet reconciliation and pairing. A snapshot of current velocity/current stack plus an old position base can produce a combination Java never sends.

## Smallest coherent next integration

Keep item physics detached until a guarded scenario can run full original base/movement semantics. A useful first runtime proof is one unmounted player and item in generated, dry chunks, no portals/fire/hazards/inside-block effects, no embedded item, no special landing/speed blocks, with ordinary static collision shapes and verified support lookup. Enforce these conditions rather than silently treating missing effects as empty. This restricted scene would establish runtime integration, not full vanilla parity.

The next native interfaces should be:

1. Shared generic `EntityBaseState`: tick and old position/angle fields, firstTick, vehicle/portal state, fire/powder-snow state, fluid depths/eye flags, health/removal/metadata effects, RNG, hasImpulse/hurtMarked, noPhysics, stuck speed and support/fall state. The level owns tickCount advancement.
2. Explicit base-tick and movement operations returning ordered world/packet effects; make their world callbacks capable of updating entity state. An immutable `&ItemState` plus `ItemMovement {position, velocity, on_ground, friction}` cannot carry all these effects.
3. Item-body operations for buoyancy, embedded-space handling, friction, ordered merges, age, the second fluid update and despawn, executed around those generic operations in the original order.
4. One mixed entity tick list and one verified spatial index for both queries and insertion/removal semantics; preserve player touch ordering and future section transitions.
5. Distinct published tracker snapshots containing position/rotation/velocity baselines and cached metadata, reconciled atomically with packet batches. Container pickup and item mutation must commit together before collect/menu effects are published.

Validation should invoke unchanged `cjh.tick` **without overriding baseTick, move, or fluid updating** for that restricted runtime scene, then compare position/velocity raw bits, support/ground/impulse/age/delay/removal, RNG consumption and emitted packet sequence over ticks. Expand world contexts only after those full-scene comparisons pass.
