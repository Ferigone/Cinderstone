# Native Main anvil runtime

`main_anvil.rs` owns one retained `AnvilMenu<NativeAnvilBinding>` per actual player. It borrows the canonical `SharedContainer` inventory and preserves the separately retained InventoryMenu cursor and 2×2 grid. A result preview is never a second stack or ItemEntity owner.

## Actual owner transaction

The outer Server operation holds the existing world/player locks. The runtime loans the one menu instance out of its map while `SharedContainer::transact_with_menu_commit` reserves the actual container revision. The mandatory native host `begin_stage` owns detached proposals; its one-shot `publish_stage` capability prepares all menu publication work before the controller installs the new UI. Failure restores the same pre-action UI and the SharedContainer rollback copy. A failed fresh opening does not retain a new UI.

Preparation validates the actual gameplay-owner certificate, native-source/configuration profile, actual player/UUID/dimension/window binding, actual lifecycle experience level and instabuild flag, each source-phase stack and inventory scan, statistic changes, owned drops, LevelEvent packets and actual entity-store publication. It does not create a replacement advancement registry, XP owner, world RNG, item registry or second live inventory. Nonempty enchantment maps (including nested contents and client predictions) are explicitly rejected until a configured actual holder/registry provider is bound. Empty maps carry no holder identity and remain admissible.

The prepared capability retains exclusive real item-store, player-RNG and gameplay borrows. After the native operation succeeds, the outer infallible closure installs the retained UI, or retires that same UI on close, before enqueueing the prepared existing PlayerEvent/Item FIFO. The Item batch interleaves actual world-add at the source Drop index, then awards Player.drop statistics. It neither emits a second item outbox nor invokes an asynchronous network writer under these locks.

Each player-slot listener uses its original phase inventory installed on the same canonical PlayerContainer. The mapping is menu slot + 6 = raw canonical player slot, for raw slots 9–44. InventoryChanged observes the pre-increment inventory and performs exactly one real `Inventory.setChanged`; this is distinct from the criterion listener. Source constructor-default input/data listeners add no invented callback. No crafted, recipe, enchantment or advancement callback is fabricated for anvil results. Close returns cursor then input0 then input1, transfers retained player-slot baselines and preserves InventoryMenu cursor/grid ownership.

OpenScreen (type 8, `container.repair`) precedes initialization callbacks/packets. Server close-window precedes removal observations. All other sync packets retain their source event position. `Broadcast` runs independently of later block validity; Click/Rename apply the real source validity gate. Incorrect windows and out-of-range clicked slots are ignored before mutation.

## Admitted production slice and remaining seams

Mutable opening/click/rename require the actual alive, unmounted creative Overworld profile, native body/default-effect source certificate, supported component identity and captured default configuration. The actual lifecycle XP level is captured even though creative source short-circuits XP consumption and wear RNG. Survival XP/wear/block mutation is unavailable; no default level or success is substituted. Broadcast/full-state/close retain their source ownership paths after a mutable profile changes, subject to actual identity/source-owner availability. Runtime uses the separately claimed finite actual Item method context; unknown/tag-dependent repair, text and enchantment-registry contexts are rejected.

Actual drop preparation also calls the actual process RandomSource factory; its process seed/clock acquisition is not rollback-capable, while the detached player/world streams are committed only on success. Actual drop preparation acquires existing chunk query readiness before entity preparation. That shared acquisition may independently mutate readiness/transport state and enqueue ChunksReady; the menu transaction does not pretend those independent readiness effects are rolled back. The central integrator explicitly accepted these existing independent acquisition boundaries. No all-world/output/process-entropy rollback is claimed. Menu/inventory/counter/player and world streams/stat/actual item-store/entity-ID/gameplay outbox effects remain prepared until validated adoption.

The five new Main modules require central mechanical module/LivePlayers fields and real dispatch, tick, cross-open, pickup, disconnect and shutdown callsites. Unexported source alone is not production integration. Comprehensive conformance remains deferred.
